### Operating conventions

These describe how the work is run. The architecture rules are in the contract.

- Approvals (decided by the user, 3 November 2026): the user approves starting an investigation, then the plan, then the merge. "Approve" covers the step it answers and nothing more.
  - **Approving a plan covers building it:** the branch, the pull request, the independent review where the rule below asks one, and fixing what the review finds. The agent comes back before the merge only if the plan itself has to change.
  - **Approving a merge names the exact head commit,** because merging redeploys production. It also covers deleting the merged branch afterwards, once it is confirmed in `main`.
  - Live-check records go into the next pull request, never a pull request of their own.
- Parallel work (decided by the user, 3 November 2026):
  - While a pull request waits for its review, CI or Render, the agent investigates the next step read-only, so its plan is ready when the current step merges.
  - At most two streams change code at once, in separate areas, each on its own branch in its own working copy. Production takes one merge at a time, each with its own live check.
  - Read-only research may run in the background; it changes nothing in the repository or in production.
  - A design demo on a branch that is never merged (W-51, the employer side) does not count toward the two streams: it changes no production code and has its own working copy (decided by the user, 3 November 2026).
- Group small work of the same risk class into one pull request, proposed in the plan (decided by the user, 3 November 2026). Security-boundary changes (sign-in, sessions, keys, the fetch policy, the public surface) stay in pull requests of their own.
- Records (decided by the user, 3 November 2026): this ledger keeps the current state and one line per merged pull request ("Done"); a step's record in a plan document is about 10 lines (what changed, the evidence, any result change, what is left); the pull request's description holds the full detail.
- Independent reviews by risk (decided by the user, 3 November 2026), each by a separate read-only agent in an isolated clone:
  - **Always:** security boundaries (the fetch policy, sign-in, sessions, secrets, the public surface); anything that writes or deletes data in bulk, or changes crawl locks, run ownership, or expiry; database schema changes; dependency or build changes that reach production; large plans before they are built; contract amendments.
  - **Self-review, CI, and tests shown to fail on the old code:** small low-risk code changes, admin display fixes, test-only changes.
  - **None:** docs-only pull requests (live records, ledger updates) and branch tidy-ups.
  - A re-review only when the fixes to a review's findings change logic, not for wording or added tests.
  - Each review is limited to about 35 minutes, reruns only the tests the change touches after each mutation, and reports what it has when time runs out.
- Work happens on a branch, through a pull request into `main`. Do not push `main` directly.
- **Merging to `main` deploys the backend.** Render redeploys automatically when `main` changes. Merge only with explicit approval. A manual "Deploy a specific commit" on Render switches Auto-Deploy off ("Auto-Deploy has been disabled to prevent accidental deploys"); seen on 23 October 2026 with the backend live on `d13d983`. After any manual Render deploy, set Settings, Build & Deploy, Auto-Deploy back to "On Commit".
- **Netlify is no longer used.** Its free credits ran out on 23 October 2026 and the user deleted the site the same day. Pull-request previews are checked on Vercel with the bypass key (UX plan, method step 4).
- After a merge: confirm `origin/main`, CI on `main`, and the Render deploy. Then fast-forward local `main`.
- Do not crawl production, write to the jobs database, or reindex search unless the user asks for that step.
- Admin checks (decided by the user, 1 November 2026): the agent never signs in, so a check that needs a signed-in admin is the user's sign-in, with the read-only browser guard on whenever the agent uses an admin page. A change to the admin gets its tests plus one production check after merging; a check on the pull request's preview as well only for high-risk admin changes (sign-in, or anything that deletes or writes in bulk) that change the frontend, said so in the plan (a preview calls the production backend, so it cannot test a backend-only change). Since 3 November 2026 (the user's decision), the signed-in production check is asked for only when a page's behaviour or data can change; a backend-only change to error messages is checked without a session. The user signs out after each check.
- A read-only database check must enforce read-only and prove it: after `psycopg2.connect`, call `conn.set_session(readonly=True)`, then run `SHOW transaction_read_only` and stop unless it returns `on`. The connection option `-c default_transaction_read_only=on` alone is ignored through the Supabase pooler (found 24 October 2026, UX-04).
- Commits must be authored by the GitHub account `AidJobs` (`git config user.name AidJobs`, `git config user.email 241161196+AidJobs@users.noreply.github.com`, set in this repository only). The repository is private and Vercel's free plan builds only commits by the project owner; commits by any other author show "Deployment was blocked" (seen on PRs #25 and #26 before the change, 21 October 2026).
- Never write a secret into a tracked file: passwords, keys, connection strings, and tokens live only in Render, Vercel, Supabase, or the user's machine. Documentation uses placeholders. CI's gitleaks job fails a pull request that adds one; a value that reaches git must be rotated, because removing it from a file does not remove it from history (W-30). The agent never prints a secret's value: checks report lengths, matches, or fingerprints only.
- Commit only the files the step names. Never stage `apps/backend/scripts/diagnose_enrichment_bias.py` or `tests/test_link_heuristics.py`. Both carry unrelated Pyright-ignore comments and stay modified and unstaged.
- The local shell is PowerShell on Windows. Use `@" "@` here-strings for commit messages, not bash heredocs. `gh --jq` filters with spaces break in PowerShell; pipe JSON to `ConvertFrom-Json` instead.
- Local tests run from `apps/backend` with `.venv311\Scripts\python.exe` (since 3 November 2026): Python 3.11.9, the version CI and Render use, from uv's own folder (`%APPDATA%\uv\python`), with `requirements-test.txt` installed hash-checked except `uvloop` (no Windows build), plus `colorama` 0.4.6, which `pytest` needs on Windows and the Linux lock does not list. ### How the crawler is built today

Recorded 19 October 2026 from the repository and the Render log.

There is one crawler. The scheduler and the admin Crawl button both enter `CrawlerOrchestrator` in `apps/backend/orchestrator.py`. Each source type has one crawler (HTML, RSS, API), and all three use the one `admit_batch` and the one writer, `persist_candidate`. That matches the contract.

Inside the HTML crawler, a listing page is read by the first of these that produces jobs (`SimpleCrawler._listing_jobs` and `crawl_source`, `crawler_v2/simple_crawler.py`):

1. The pipeline extractor, only when `core/rollout_config.py` selects the source. Dormant: see W-23.
2. The UNICEF reader, then paging through "More Jobs". UNICEF only, chosen by the `unicef.org` host (PRs #11, #13, #14). If it finds nothing or fails, the general reader.
3. The general rule-based reader. Every other source, including ICRC and Oxfam.

Since PR #58 (27 October 2026) there is no AI step and no plugin registry (W-11, W-14). Before it, AI extraction was tried first and failed on every crawl after 18 October, and the plugin registry ran only with AI off and could not be built.

Job pages, for a listing of 1–50 candidates or any UNDP listing (`enrich_job_from_detail_page`): UNICEF is skipped, UNDP has its own rules, and every other site uses the detail-page reader (PRs #8, #9).

The organisation-specific exceptions (UNICEF and UNDP, chosen by web address) are the part that does not scale. The direction is platform readers chosen by what the page shows, not by organisation (W-19).

Rule, agreed 19 October 2026: do not edit a source's URL to work around one site's behaviour. Knowledge such as a platform's page size or paging belongs once in that platform's reader, and sources keep their normal listing URLs. The earlier suggestion to change the UNICEF source URL to `?page-items=50` was withdrawn for this reason.

## Terms used in this project

- **`thin_vacancy`**: a link that looks like a job but carries no location, deadline, or contract type. Rejected.
- **`no_qualifying_family`**: an ordinary page link with nothing that marks it as a vacancy. Rejected.
- **`root_careers_page`**, **`social_profile`**, **`vendor_badge`**: a careers home page, a social media link, or a "powered by" badge. Rejected.
- **NC**: `consecutive_nochange` in the admin, the number of crawls in a row that saved nothing.
- **`HTTP 0`**: the crawler received no response at all, for example a timeout, connection error, or a request blocked by the fetch policy.
- **Suppressed, or hidden**: `deleted_at` is set by an admin. A recrawl never clears it.
- **Expired**: a lifecycle state the contract allows only after the W-06 policy is approved. Not used today.
